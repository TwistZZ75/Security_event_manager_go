# SIEM --- система сбора, анализа и реагирования на события безопасности

Выпускная квалификационная работа
Направление: **Информационная безопасность**

## Краткое описание

Данный проект представляет собой SIEM-систему для централизованного
сбора, нормализации и анализа событий безопасности с конечных устройств.

Система реализована на **Go** и состоит из агентов, серверной части и
веб-интерфейса. Агенты собирают события из системных журналов и передают
их на сервер по **gRPC**. Сервер нормализует полученные события,
сохраняет их в PostgreSQL и обрабатывает с помощью движка корреляции,
работающего на основе JSON-правил.

При срабатывании правила система формирует алерт и, в зависимости от
настроек правила, может выполнить автоматическое реагирование: отправить
уведомление, выполнить команду на агенте и т.д.

Проект разработан в рамках выпускной квалификационной работы и
предназначен в том числе для демонстрации навыков разработки
backend-приложений на Go, работы с PostgreSQL, gRPC, REST API,
WebSocket, Docker, Redis, JWT-аутентификацией и построения системы
корреляции событий.

## Архитектура

``` text
Агент
  │
  │ gRPC
  ▼
SIEM Server
  ├── нормализация событий
  ├── Rule Engine
  │     ├── conditions
  │     ├── count
  │     ├── threshold
  │     └── sequence
  ├── Alerts / Actions
  ├── REST API
  └── WebSocket
       │
       ▼
React Dashboard

SIEM Server ── PostgreSQL
           └── Redis
           └── Telegram / Email
```

Агенты передают события на сервер по gRPC. Сервер нормализует события,
сохраняет их в PostgreSQL и передаёт в движок корреляции. Правила
загружаются из PostgreSQL и кешируются в Redis. При срабатывании правила
создаётся алерт и выполняются настроенные действия. Веб-интерфейс
использует REST API и WebSocket.

## Основной функционал

### Агенты

Агенты работают как фоновые сервисы ОС и отвечают за сбор событий и
выполнение команд, полученных от сервера.

Поддерживаются и тестировались:

-   **Windows 10**
    -   Security Event Log
    -   Sysmon
-   **Ubuntu 24**
    -   syslog
    -   authlog
    -   Suricata

Поддержка других ОС и источников журналов не гарантируется, так как они
не тестировались в рамках проекта.

Агент может выполнять команды сервера:

-   блокировка учётной записи;
-   разблокировка учётной записи;
-   отключение сети;
-   изоляция хоста;
-   завершение процесса.

Конфигурация агента задаётся через YAML-файл. Конфигурационный файл
необходимо разместить в одной директории с установщиком/исполняемым
файлом агента.
Для windows это файлы \agent_windows\agent\siem-agent.exe и agent_windows\agent\agent_config.yaml
Для Ubuntu это файлы  agent_linux\agent\SIEM_agent и agent_linux\agent\agent_config.yaml

### Сервер

Сервер отвечает за:

-   приём событий через gRPC;
-   нормализацию событий;
-   сохранение данных в PostgreSQL;
-   загрузку и кеширование правил;
-   корреляцию событий;
-   создание алертов;
-   выполнение действий;
-   отправку уведомлений;
-   управление агентами и командами;
-   REST API;
-   WebSocket.

### Движок корреляции

Правила хранятся в JSON-формате.

Поддерживаются типы агрегации:

#### Count

Подсчёт количества событий за заданное временное окно.

Например, правило может срабатывать при пяти неудачных
SSH-аутентификациях с одного компьютера за две минуты.

#### Threshold

Накопление и сравнение числовых значений.

Поддерживаемые операции:

-   `sum` --- сумма;
-   `max` --- максимум;
-   `avg` --- среднее значение;
-   `distinct_count` --- количество уникальных значений.

#### Sequence

Проверка последовательности событий:

``` text
A → B → C
```

События должны происходить в заданном порядке и в пределах временного
окна.

### Условия правил

Поддерживаются операторы:

-   `equals`
-   `not_equals`
-   `contains`
-   `not_contains`
-   `starts_with`
-   `ends_with`
-   `regex`
-   `in`
-   `not_in`
-   `greater_than`
-   `less_than`
-   `greater_or_equal`
-   `less_or_equal`
-   `ip_equals`
-   `ip_in_range`

Поддерживаются поля нормализованного события:

-   `id`
-   `pc_name`
-   `username`
-   `event_description`
-   `event_category`
-   `process_name`
-   `severity`
-   `timestamp`
-   `os`
-   `source`
-   `raw_log`

Для значений внутри JSON `raw_log` поддерживается dot-нотация, например:

``` text
raw_log.bytes_toserver
```

### Пример правила

``` json
{
  "id": "462935bdb7b627c3eb93feac9f78a7c09e65753fb83b361c0ced15c3fa0936ea",
  "name": "SSH Brute Force",
  "os": "",
  "enabled": true,
  "severity": "high",
  "conditions": [
    {
      "field": "event_category",
      "operator": "equals",
      "value": "SSH Auth Failure"
    }
  ],
  "aggregation": {
    "type": "count",
    "field": "pc_name",
    "time_window": "2m",
    "threshold": 5
  },
  "actions": [
    {
      "type": "notify",
      "parameters": {
        "channels": [
          "telegram"
        ]
      }
    }
  ],
  "tags": [
    "ssh",
    "brute-force",
    "authentication",
    "linux"
  ],
  "created_by": "web",
  "created_at": "2026-03-16T13:27:29.897722Z",
  "updated_by": "noone",
  "updated_at": "2026-08-27T00:00:34.073645Z",
  "trigger_count": 0
}
```

В данном примере правило отслеживает `SSH Auth Failure`, группирует
события по `pc_name` и срабатывает при пяти событиях за две минуты.
После срабатывания создаётся алерт и отправляется уведомление в
Telegram.

## Алерты

При срабатывании правила создаётся алерт с информацией о правиле,
severity, описанием, данными события, временем создания и текущим
статусом.

Статусы:

``` text
open
  ↓
acknowledged
  ↓
resolved / false_positive
```

Уведомления могут отправляться через Telegram бота и email.

## Веб-интерфейс

Веб-интерфейс реализован на React + TypeScript.

Возможности:

-   JWT-аутентификация;
-   просмотр событий;
-   просмотр алертов;
-   просмотр агентов;
-   просмотр правил;
-   создание и редактирование правил;
-   включение и отключение правил;
-   изменение статусов алертов;
-   просмотр пользователей;
-   управление пользователями.

Для событий и алертов используется WebSocket для получения обновлений в
реальном времени. Правила и информация об агентах загружаются через REST
API.

### Ролевая модель

Предусмотрены роли:

-   **Администратор** --- полный доступ и управление пользователями.
-   **Аналитик** --- основной функционал без управления пользователями.
-   **Наблюдатель** --- роль предусмотрена моделью доступа; ограничение
    прав находится в разработке.

## Хранение данных

PostgreSQL используется для хранения:

-   пользователей;
-   refresh-токенов;
-   правил;
-   состояния правил;
-   агентов;
-   нормализованных событий;
-   алертов;
-   очереди команд;
-   журнала выполнения действий.

Структура базы создаётся из:

``` text
migrations/migration.sql
```

Демонстрационные данные находятся в:

``` text
migrations/testdata.sql
```

Пользователь намеренно не добавляется в `testdata.sql`: после запуска
системы пользователь регистрируется через штатную функцию регистрации.

## Redis

Redis используется для кеширования часто читаемых данных, в частности
правил.

Логика загрузки правил:

``` text
Redis
  │
  ├── cache hit ──► правила загружены
  │
  └── cache miss
          │
          ▼
     PostgreSQL
          │
          ▼
        Redis
```

Ключ кеша правил:

``` text
rules:all
```

TTL:

``` text
5 минут
```

При изменении правил кеш инвалидируется и правила загружаются заново.

## Запуск

### Требования

Необходимы:

-   Docker;
-   Docker Compose.

Для тестирования сбора событий также потребуется запустить агент на
поддерживаемой ОС.

### 1. Клонирование

``` bash
git clone <URL_РЕПОЗИТОРИЯ>
cd <НАЗВАНИЕ_РЕПОЗИТОРИЯ>
```

### 2. Создание `.env`

Перейдите в директорию сервера:

``` bash
cd siem-server
```

Linux/macOS:

``` bash
cp .env.example .env
```

Windows PowerShell:

``` powershell
Copy-Item .env.example .env
```

Заполните необходимые значения в `.env`.

Затем вернитесь в корень проекта:

``` bash
cd ..
```

### 3. Запуск

Запустить все компоненты:

``` bash
docker compose up --build
```

Или в фоне:

``` bash
docker compose up --build -d
```

Docker Compose запускает:

-   PostgreSQL;
-   Redis;
-   SIEM Server;
-   React Frontend.

PostgreSQL и Redis имеют healthcheck, поэтому сервер запускается после
успешной проверки зависимостей.

### 4. Доступ к системе

Веб-интерфейс:

``` text
http://localhost:3000
```

REST API:

``` text
http://localhost:8080
```

gRPC:

``` text
localhost:5000
```

PostgreSQL с хоста:

``` text
localhost:5433
```

Внутри Docker-сети сервер использует:

``` text
postgres:5432
redis:6379
```

### 5. Регистрация

После запуска откройте:

``` text
http://localhost:3000
```

Зарегистрируйте пользователя через интерфейс приложения и выполните
вход.

Пользователь не создаётся автоматически при инициализации базы данных.

### 6. Установка и запуск агентов

Агенты SIEM предназначены для сбора событий на клиентских машинах и передачи нормализованных данных на SIEM-сервер по gRPC.

Поддерживаются следующие ОС:

- **Windows 10** — сбор событий из журналов `Security` и `Sysmon`.
- **Ubuntu 24** — сбор событий из `syslog`, `authlog` и `Suricata`.

> Другие версии и дистрибутивы ОС в рамках проекта не тестировались, поэтому гарантировать их работу нельзя.

## Общая схема установки

Для каждой клиентской машины необходимо:

1. Получить исполняемый файл агента для соответствующей ОС.
2. Создать рядом с агентом конфигурационный файл `config.yaml`.
3. Указать в конфигурации адрес и порт SIEM-сервера.
4. Установить агент как системный сервис.
5. Запустить сервис.
6. Проверить, что агент подключился к серверу и начал передавать события.

Агент не требует установки Docker на клиентской машине. Docker используется для развёртывания серверной части системы.

# Linux (Ubuntu 24)

## 1. Подготовка

Скопируйте Linux-агент и конфиг на целевую машину. Для работы агенту необходимы права, достаточные для установки systemd-сервиса и чтения отслеживаемых журналов.

Для Ubuntu это файлы  agent_linux\agent\SIEM_agent и agent_linux\agent\agent_config.yaml

Рекомендуемый каталог установки:

```text
/usr/local/bin/
```

Поместите в этот каталог:

```text
siem-agent
config.yaml
```

Конфигурационный файл должен находиться в той же директории, откуда агент загружает настройки.

## 2. Настройка `config.yaml`

В конфигурации необходимо указать адрес и порт SIEM-сервера.

Пример:

```yaml
server:
  address: "192.168.1.100"
  port: "5000"
```

Также в конфигурации должны быть указаны параметры, необходимые коллекторам Linux-журналов.

Убедитесь, что машина с агентом может установить TCP-соединение с сервером по указанному gRPC-порту.

## 3. Установка systemd-сервиса

Перейдите в каталог агента:

```bash
cd /usr/local/bin
```

Запустите установку:

```bash
sudo ./siem-agent install
```

При успешной установке агент сообщит:

```text
Service installed successfully
```

После этого агент будет зарегистрирован как systemd-сервис.

## 4. Запуск агента

Запустите созданный сервис через systemd:

```bash
sudo systemctl start siem-agent
```

Проверьте его состояние:

```bash
sudo systemctl status siem-agent
```

Для просмотра логов:

```bash
sudo journalctl -u siem-agent
```

После запуска агент должен подключиться к SIEM-серверу и запустить сборщики событий.

## 5. Автоматический запуск

Чтобы агент автоматически запускался после перезагрузки системы:

```bash
sudo systemctl enable siem-agent
```

Проверить состояние:

```bash
sudo systemctl is-enabled siem-agent
```

## 6. Удаление агента

Для удаления systemd-сервиса:

```bash
sudo /usr/local/bin/siem-agent uninstall
```

Также поддерживается команда:

```bash
sudo /usr/local/bin/siem-agent remove
```

В конфигурации необходимо указать адрес и порт SIEM-сервера.

Установка Windows-агента выполняется через регистрацию Windows Service.

После установки службы в системе должна появиться служба:

```text
SIEMAgent
```

Проверить её наличие можно через:

```text
Win + R → services.msc
```

После этого найдите:

```text
SIEMAgent
```

и запустите службу.

## 4. Запуск и проверка

После запуска службы агент начинает работу в качестве фонового процесса.

Проверить состояние службы можно через:

```text
services.msc
```

```text
SIEMAgent
```

Агент должен подключиться к SIEM-серверу и запустить сбор событий из поддерживаемых источников.

## 5. Сбор событий

В текущей реализации Windows-агент предназначен для сбора событий из:

- `Security`;
- `Sysmon`.

После успешного подключения события передаются на сервер по gRPC, где они обрабатываются движком нормализации и корреляции.

# Проверка работы агента

После запуска агента проверить работу можно на стороне SIEM-сервера и через веб-интерфейс.

Основные признаки корректной работы:

1. Агент успешно запускается как системный сервис.
2. Агент устанавливает gRPC-соединение с сервером.
3. Сервер получает события от агента.
4. События появляются в веб-интерфейсе.
5. При выполнении условий правила корреляции создаётся alert.

Для проверки работы корреляции можно использовать тестовое правило и сгенерировать на клиентской машине соответствующие события.

### 7. Тестовые данные

При первом создании PostgreSQL-контейнера выполняется:

``` text
migrations/migration.sql
```

Тестовые данные из:

``` text
migrations/testdata.sql
```

можно загрузить отдельно после создания структуры базы.

Если база уже запускалась и требуется полностью пересоздать тестовую
среду:

``` bash
docker compose down -v
docker compose up --build
```

> `docker compose down -v` удаляет Docker volumes, включая данные
> PostgreSQL. Используйте команду только в тестовой среде.

### 8. Проверка работы

Рекомендуемый сценарий демонстрации:

1.  Запустить Docker Compose.
2.  Открыть веб-интерфейс.
3.  Зарегистрировать пользователя.
4.  Выполнить вход.
5.  Проверить страницы агентов, правил, событий и алертов.
6.  Создать тестовое правило.
7.  Запустить агент на тестовой машине.
8.  Сгенерировать событие, соответствующее условию правила.
9.  Проверить появление события в интерфейсе.
10. Проверить срабатывание Rule Engine.
11. Проверить создание алерта.
12. Проверить уведомление, если оно настроено.
13. Проверить выполнение action агентом, если действие указано в
    правиле.

## Безопасность

Проект предназначен прежде всего для учебных, исследовательских и
демонстрационных целей.

Для эксплуатации в реальной инфраструктуре необходимо дополнительно
реализовать и проверить:

-   TLS для сетевого взаимодействия;
-   безопасное хранение секретов;
-   ротацию ключей и токенов;
-   полноценную RBAC-модель;
-   аудит административных действий;
-   защиту API;
-   строгую валидацию команд, выполняемых агентами;
-   резервное копирование PostgreSQL;
-   мониторинг компонентов.

Особое внимание необходимо уделить действиям реагирования, поскольку
некоторые команды могут изменить состояние конечной системы или
отключить её сетевое соединение.
